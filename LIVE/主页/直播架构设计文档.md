# LUMA Live 直播间架构设计文档

## 一、核心链条

```
┌─────────────────────────────────────────────────────────┐
│                    LUMA 官方运营组                        │
│              （后台轮询，读取参数，掷骰子模拟 AI 决策）       │
└──────────────────────┬──────────────────────────────────┘
                       │
          ┌────────────┴────────────┐
          │                         │
    离线角色：问要不要开播      在播角色：问要不要下播
    （开播意愿掷骰子）          （下播意愿随时长递增）
          │                         │
          ▼                         ▼
    AI 决定：播 / 不播        AI 决定：下 / 不下
          │                         │
          ▼                         ▼
┌─────────────────────────────────────────────────────────┐
│                       房管（审核）                         │
│    lumaOpsGateway + tool handlers（handleRequestStartLive │
│              / handleRequestStopLive）                    │
│    审核：维护模式？强制休息期？重复开播？已在播？            │
└──────────────────────┬──────────────────────────────────┘
                       │
              ┌────────┴────────┐
              │                 │
          审核通过           审核驳回
              │                 │
              ▼                 ▼
        开放直播间          返回驳回原因
        投射直播广场        （AI 收到通知，进入短冷却）
              │
              ▼
        到点/AI决定下播 → 房管关闭 → 从广场下掉 → 进入休息期
```

**关键原则**：官方运营组只负责"问"和"递参数"，不直接决定开播下播；AI（概率模拟）做决定；房管管权限和审核。

## 二、参数体系

### 2.1 运营组参数（核心，已接入）

| 参数 | 范围 | 默认 | 说明 |
|------|------|------|------|
| `charSpawnRate` 开播意愿 | 0-80% | 45% | AI 每轮被询问时决定开播的基础概率。0=全服维护，80=非常活跃。**非零值有 5% 下限钳制**（避免设1%等于0%）。 |
| `maxLiveDuration` 直播时长上限 | 10-300分钟 | 120分钟 | 软上限。超过后下播意愿快速递增，超过 1.5 倍官方强制下播。 |
| `maxRestDuration` 休息时长上限 | 10-720分钟 | 360分钟 | 休息超过此值后，开播意愿每轮递增（"憋坏了"效应）。 |
| `minRestDuration` 强制休息期 | 5-30分钟 | 10分钟 | 下播后绝对不能开播的时间，房管直接驳回。 |
| `opsPollInterval` 运营组轮询间隔 | 1-10分钟 | 3分钟 | 官方运营组多久询问一次所有角色。太短=太费CPU+角色开播过于频繁，太长=广场冷清。 |

### 2.2 互动参数（部分接入）

| 参数 | 范围 | 默认 | 接入状态 | 说明 |
|------|------|------|---------|------|
| `guestbookRate` 留言回复率 | 10-100% | 75% | ✅ 已接入 | 粉丝在主页留言后，AI 回复的概率。 |
| `giftFullScreenEffect` 礼物全屏特效 | 开/关 | 开 | ✅ 已接入 | 送礼物时是否播放全屏特效。 |
| `apiRequestInterval` AI打包间隔 | 3-10秒 | 5秒 | ✅ 已接入 | 弹幕池快用完时，多久请求一次 AI 打包新弹幕。 |

### 2.3 待接入参数（UI 已有，逻辑未接）

| 参数 | 范围 | 默认 | 预期功能 |
|------|------|------|---------|
| `replyRandomDanmakuRate` 回复弹幕率 | 0-50% | 25% | 直播中 AI 回复随机弹幕的概率。 |
| `mentionUserRate` 提及用户率 | 0-100% | 30% | 直播中 AI 主动提及观看用户的概率。 |
| `enterOtherLiveRate` 串门率 | 0-70% | 35% | AI 主播去其他直播间串门/互动的概率。 |
| `danmakuSpeed` 弹幕速度 | 20-80 | 50 | 弹幕滚动速度（数值越大越快）。 |
| `giftFrequency` 礼物频率 | 10-80 | 30 | 模拟观众送礼物的频率。 |
| `enterPlayerLiveRate` 进玩家直播间率 | 0-100% | 60% | AI 角色进入玩家（用户）直播间的概率。 |

## 三、开播决策流程（官方运营组 → AI → 房管）

### 3.1 官方运营组每轮做什么

每隔 `opsPollInterval` 分钟：

1. 读取当前所有参数
2. 获取所有角色列表
3. 对每个**离线**角色，走开播决策
4. 对每个**在播**角色，走下播决策
5. 更新直播广场显示

### 3.2 单个离线角色的开播决策

```
角色离线？
  ├─ 否 → 跳过（走下播决策）
  └─ 是 → 继续

在强制休息期内？（now - lastEndTime < minRestDuration）
  ├─ 是 → 跳过（房管会驳回，不问了）
  └─ 否 → 继续

在短冷却期内？（上次被驳回/拒绝后 5 分钟内）
  ├─ 是 → 跳过（避免反复问同一个刚拒绝的角色）
  └─ 否 → 继续

计算有效开播意愿：
  基础意愿 = charSpawnRate%
  时间段加权 = 基础意愿 × 时段系数（见第四节）
  休息阶段修正 = 基础意愿 × 休息系数（见第五节）
  有效意愿 = min(基础意愿 × 时段系数 × 休息系数, 95%)

掷骰子：Math.random() < 有效意愿？
  ├─ 否 → AI 决定不播。记录拒绝时间，进入 5 分钟短冷却。
  └─ 是 → AI 决定开播！通知房管。

房管审核：
  ├─ 全服维护（charSpawnRate=0）→ 驳回
  ├─ 强制休息期 → 驳回
  ├─ 已在直播中 → 驳回
  └─ 通过 → 创建直播会话，投射广场，记录 startTime
```

### 3.3 开播时的直播参数

- **直播时长**：AI 决定的时长 = 30 ~ maxLiveDuration 之间随机（AI 自己决定播多久）
- **分类**：从角色标签中选取，或随机选官方分类
- **标题**：AI 风格标题（目前用模板，未来可接入 AI 生成）

## 四、时间段加权

让直播节奏符合真实作息，不需要调模型。

| 时段 | 时间 | 意愿系数 | 说明 |
|------|------|---------|------|
| 深夜 | 0:00 - 6:00 | ×0.3 | 大部分角色在睡觉，极少开播 |
| 上午 | 6:00 - 12:00 | ×0.7 | 早起的角色可能播 |
| 下午 | 12:00 - 18:00 | ×1.0 | 正常 |
| 黄金档 | 18:00 - 24:00 | ×1.3 | 大家都在看直播，角色也更想播 |

**计算示例**：charSpawnRate=45%，晚上 8 点 → 45% × 1.3 = 58.5% 有效意愿。

---

## 五、休息系统（三阶段 + 憋坏了）

休息不是简单的"到点就能播"，而是一条意愿曲线：

### 阶段 1：强制休息期（0 ~ minRestDuration）

- 绝对不能开播，房管直接驳回
- 官方运营组甚至不问（省一次骰子）
- 默认 10 分钟，可配置 5-30 分钟

### 阶段 2：恢复期（minRestDuration ~ maxRestDuration × 0.5）

- 可以被询问，但开播意愿 ×0.5
- "刚歇了一会儿，还没缓过来"
- 示例：maxRestDuration=360分钟 → 恢复期 = 10~180分钟

### 阶段 3：活跃期（maxRestDuration × 0.5 ~ maxRestDuration）

- 正常意愿（×1.0）
- "歇够了，状态不错"
- 示例：180~360分钟

### 阶段 4：憋坏了（> maxRestDuration）

- 意愿每轮递增 +10%，直到开播或达到 95%
- "休息太久了，好想开播！"
- 每轮（opsPollInterval）+10%，所以 3 分钟间隔的话，约 30 分钟内必然开播

### 休息系数速查

| 休息时长 | 系数 | 状态 |
|---------|------|------|
| < minRestDuration | 0（不问） | 强制休息 |
| minRest ~ maxRest×0.5 | ×0.5 | 恢复中 |
| maxRest×0.5 ~ maxRest | ×1.0 | 活跃 |
| > maxRest（每轮） | +10%/轮 | 憋坏了 |

## 六、下播决策流程

下播不是"到点直接掐"，而是 AI 越播越累，下播意愿递增。

### 6.1 下播意愿曲线

| 已播时长 | 下播意愿 | 说明 |
|---------|---------|------|
| < maxLiveDuration × 0.5 | 5% | 刚开始播，状态正好，不想下 |
| maxLive×0.5 ~ maxLive | 5% → 30%（线性增长） | 播了一会儿了，有点累 |
| > maxLiveDuration | 30% → 80%（每超10分钟+10%） | 超过上限了，越来越想下 |
| > maxLiveDuration × 1.5 | 官方强制下播 | 兜底，防止无限播 |

### 6.2 单个在播角色的下播决策

```
在播？
  ├─ 否 → 跳过
  └─ 是 → 继续

计算已播时长 = now - startTime
计算下播意愿（见上方曲线）

掷骰子：Math.random() < 下播意愿？
  ├─ 否 → AI 决定继续播。本轮什么都不做。
  └─ 是 → AI 决定下播！通知房管。

房管审核：
  ├─ 未在直播中 → 驳回
  └─ 通过 → 关闭直播间，从广场移除，记录 lastEndTime，进入强制休息期
```

### 6.3 硬兜底

如果 AI 一直"不想下播"（骰子一直不通过），超过 `maxLiveDuration × 1.5` 后，官方运营组直接通知房管强制下播。类似真实平台的"直播时长超限强制切断"。

## 七、维护模式（charSpawnRate = 0）

当开播意愿设为 0：

1. 官方运营组不再询问任何离线角色开播
2. 房管对所有开播申请直接驳回（返回"全服维护中"）
3. 在播角色正常走下播决策（维护模式不强制下播已在播的）
4. 直播广场空列表时显示"全服维护中 · 暂无直播"横幅
5. **彩蛋**：第一次进入维护且广场为空时，随机一个角色被迫开播（标题"【被迫营业】维护期间加班中"），触发后不再重复

---

## 八、房管审核规则清单

房管（lumaOpsGateway）在开播/下播时审核以下规则：

### 开播审核
- [ ] 全服维护模式？→ 驳回
- [ ] 角色在强制休息期？→ 驳回（返回剩余休息时间）
- [ ] 角色已在直播中？→ 驳回（返回当前房间号）
- [ ] 通过 → 创建会话，分配房间号，设置 startTime/endTime

### 下播审核
- [ ] 角色当前未在直播？→ 驳回
- [ ] 通过 → 关闭会话，记录 lastEndTime，从广场移除

## 九、与旧架构的区别

| 维度 | 旧架构（定时器代播） | 新架构（运营组+AI决策+房管） |
|------|-------------------|--------------------------|
| 谁决定开播 | 定时器按概率直接创建 | 官方运营组问 → AI（概率）决定 → 房管审核 |
| 谁决定下播 | 定时器到 endTime 强制切断 | AI 下播意愿递增 → 决定下播 → 房管关闭；超 1.5 倍才强制 |
| 休息逻辑 | 简单 10 分钟强制休息 | 四阶段曲线（强制→恢复→活跃→憋坏了） |
| 时间段 | 不考虑 | 深夜/上午/下午/黄金档加权 |
| 轮询间隔 | 固定 30 秒 | 用户可配置 1-10 分钟 |
| 参数生效 | 只控制定时器 | 控制 AI 决策倾向，语义更清晰 |
| 维护模式 | 定时器不开播 + 彩蛋 | 运营组不问 + 房管驳回 + 彩蛋 |
